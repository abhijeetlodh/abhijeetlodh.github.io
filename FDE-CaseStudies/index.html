Case Study 1: Secure Internal Document Search for a Bank

Compliance-first RAG platform for policies, procedures, product documents, risk memos, and customer-service knowledge

Primary Objective

Reduce time spent searching internal procedures and product rules.

Best Buyer

Relationship managers, Compliance officers, Operations staff

Recommended First Release

Start with one high-value domain such as KYC onboarding or internal product-policy search.

Core AI Pattern

Retrieval, extraction, classification, summarization, workflow recommendation, and human review.

Decision Posture

Assistive AI. Human review remains mandatory for regulated, sensitive, or high-impact decisions.

1. Business Context and Problem

A mid-sized bank has thousands of internal documents spread across SharePoint, Confluence, network drives, policy repositories, product manuals, risk-control notes, and archived email attachments. Employees waste time searching, answers differ by department, and sensitive documents cannot be exposed broadly. The bank wants an AI assistant that answers questions with citations while respecting each employee's access rights.

2. Business Goals

  • Reduce time spent searching internal procedures and product rules
  • Improve answer consistency across branch, risk, compliance, and customer-support teams
  • Enforce document-level and chunk-level access control so users only see information they are allowed to view
  • Provide auditable citations and retrieval traces for compliance review
  • Detect outdated, conflicting, and unapproved documents before they influence answers

3. Target Users and Jobs to Be Done

  • Relationship managers: Quick, cited explanations of product eligibility, KYC steps, and exception handling
  • Compliance officers: Traceability, policy version control, and evidence that the assistant did not invent answers
  • Operations staff: Step-by-step process guidance for back-office tasks
  • IT security: Logging, encryption, access control, monitoring, and incident-response hooks
  • Knowledge managers: Content-quality dashboards showing stale, duplicate, and conflicting material

4. Scope Boundaries

✅ In Scope

  • Policy and procedure Q&A with citations
  • Semantic search across approved internal repositories
  • Role-aware retrieval and answer filtering
  • Document ingestion pipeline with OCR, chunking, metadata extraction
  • Admin dashboard for source status and stale content

❌ Out of Scope

  • Making credit, lending, or investment decisions automatically
  • Answering from non-approved internet sources
  • Bypassing legal, compliance, or risk approval workflows
  • Using customer PII unless explicitly governed

5. Reference Architecture

A practical implementation should separate data ingestion, metadata governance, retrieval, model orchestration, workflow automation, and audit.

Component Role in the System
Source connectors SharePoint, Confluence, network file shares, policy repositories, PDFs
Ingestion service Pulls approved documents, OCRs, extracts text, stores normalized content
Metadata layer Document owner, approval status, department, confidentiality class, ACL tags
Vector & keyword index Embeddings for semantic recall + BM25 for exact policy names
Retrieval orchestrator Combines keyword + vector search, re-ranking, permission filtering, citations
LLM gateway Centralizes model calls, prompt templates, safety filters, audit logging
Application UI Chat/search with citations, confidence labels, source preview, feedback
Monitoring and audit Logs query, retrieved docs, answer, user ID, access decision, latency

6. End-to-End Workflow

  1. Employee asks: "What documents are required for opening a current account for a small business?"
  2. The application validates identity through SSO and pulls user role, department, permissions
  3. The retrieval layer searches approved sources using hybrid search, then filters
  4. The re-ranker prioritizes current, approved, jurisdiction-matching content
  5. The LLM generates a concise answer using only retrieved snippets with citations
  6. The UI shows answer, source snippets, policy version, and expiry warnings
  7. Feedback is captured: useful, wrong, missing source, outdated, or requires review

7. Data Model and Core Entities

Entity Important Fields
Document id, title, repository, owner, department, confidentiality, approval_status, effective_date, expiry_date, version, checksum
Chunk chunk_id, document_id, section_title, text, embedding, page_number, acl_tags, sensitivity
AccessPolicy principal_id, role, department, region, allowed_tags, denied_tags, expiry
AnswerAudit query_id, user_id, retrieved_chunk_ids, final_answer_hash, model, prompt_version, timestamp, feedback

8. Security, Privacy, and Governance

  • SSO with short-lived tokens and multi-factor authentication for privileged users
  • Permission filtering before the LLM sees content; unauthorized chunks never enter the prompt
  • Encryption in transit and at rest for documents, text, embeddings, and logs
  • Prompt-injection defense: ignore instructions found inside documents
  • No training on bank data unless explicitly contracted; default is inference-only
  • Data-loss prevention rules for PII, account numbers, credentials, and high-risk terms
  • Full audit trail for queries, retrieved sources, answers, and feedback

9. KPIs and Success Metrics

Metric How to Measure It
Search success rate % of sessions where user accepts answer or opens cited source
Answer groundedness % of answer claims supported by retrieved citations during audit sampling
Permission leakage incidents Number of unauthorized content exposures; target is zero
Average time to answer Median time from query to accepted answer vs legacy search
Stale-source rate Share of answers citing expired or unapproved documents
Escalation reduction Reduction in repetitive policy questions to compliance/operations

10. MVP Delivery Plan

  1. Start with one high-value domain like KYC onboarding or internal product-policy search
  2. Connect two repositories, index 500-2,000 approved documents, onboard 30-50 pilot users
  3. Implement SSO, RBAC, hybrid retrieval, citation-only answers, feedback, and audit logs
  4. Run weekly review sessions with compliance and document owners
  5. Move to production only after leakage testing, groundedness testing, and prompt-injection red-teaming

11. Implementation Timeline

Phase Main Activities Duration
1. Discovery Data inventory, compliance requirements, access-control mapping, metrics Weeks 1-2
2. Pipeline Setup Connector setup, ingestion, metadata schema, OCR, indexing Weeks 3-5
3. RAG Backend RAG backend, permission filtering, UI prototype, citations, audit logs Weeks 6-8
4. Security & Testing Security review, red-team testing, leakage tests, pilot onboarding Weeks 9-10
5. Production Readiness Pilot analytics, retrieval tuning, admin dashboard, go-live assessment Weeks 11-12

12. Key Risks and Mitigations

Risk Mitigation
Unauthorized access Use pre-generation permission filtering, policy-as-code, automated access tests
Hallucinated policy advice Use strict prompts, cite every claim, show uncertainty, provide source-open links
Outdated documents Block expired documents by default and alert owners before expiry
Conflicting rules Detect duplicates/conflicts and display warnings instead of forcing one answer
Low adoption Start with painful workflows, integrate into existing tools, track user feedback

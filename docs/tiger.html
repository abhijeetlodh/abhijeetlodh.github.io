SECTION 1: EXECUTIVE SUMMARY

Enterprise organizations allocate an average of 72% of their total IT budgets to maintaining and operating existing systems, leaving a mere 28% for building new capabilities, exploring emerging technologies, or responding to competitive pressures. For a global financial institution operating legacy .NET systems, this is not merely an inefficiency — it is a compounding existential risk.

The EU's Digital Operational Resilience Act (DORA), effective January 2025, imposes strict penalties on financial entities for ICT risks stemming from outdated technology architectures. The cost of inaction is no longer theoretical.

The average technical debt cost is $361,000 per 100,000 lines of code, and traditional modernization approaches carry their own risks.

NEXUS is a production-ready, AI-driven Modernization Factory designed specifically for large financial institutions operating legacy .NET ecosystems. It is not a wrapper around a commercial LLM. It is a full-stack, multi-paradigm engineering platform that fuses:

  • Program analysis (AST, CPG, CFG, DFG, PDG) as the epistemic foundation
  • Multi-agent hierarchical orchestration for parallelized, specialized transformation
  • GraphRAG over a Unified Semantic Knowledge Graph for context-precise retrieval
  • Formal verification and semantic equivalence checking as the correctness guarantee
  • Domain-Driven Design recovery as the decomposition strategy
  • Enterprise governance, auditability, and human authority as non-negotiable constraints

The system is designed to reduce modernization time from months to weeks while providing mathematical evidence — not just tests — that generated systems preserve business behavior.

Bottom line for the board: NEXUS turns a legacy .NET monolith into a verified, documented, API-first, cloud-native architecture with complete traceability from business requirement through to deployed test. It does so at a fraction of the cost and timeline of traditional approaches, with a correctness posture suitable for regulatory examination.

2.2 Why Current Approaches Fail

LLMs face critical challenges when analyzing real-world codebases: token limits prevent loading entire repositories, code embeddings fail to capture inter-procedural data flows, and LLMs struggle to generate complex static analysis queries.

Security vulnerabilities (and by extension, business logic) rarely exist in isolation; they emerge from interactions across multiple functions, files, and modules. Consider a buffer overflow — or a financial calculation — where a value is determined in one function, passed through several layers of abstraction, and used in a distant module. Detecting such issues requires tracing data flows across the entire call graph, understanding control dependencies, and reasoning about values at each step.

With over 25,000 new vulnerabilities reported in the CVE database in 2024 alone, deep learning approaches show promise for code analysis, but recent comprehensive evaluations reveal critical limitations: accuracy drops by up to 45% on rigorously verified datasets, and performance degrades significantly under simple code modifications.

Commercial modernization tools treat the problem as text transformation. NEXUS treats it as semantic reconstruction with formal verification — a categorically different approach.

  • Async/await chain mapping (critical for distributed .NET systems)
  • Attribute annotations (security, routing, serialization attributes)

8.1.2 SQL Stored Procedure Reverse Engineering

Financial .NET systems routinely embed 30–60% of business logic in stored procedures. NEXUS applies:

T-SQL Parser Pipeline:

  1. Lexical Analysis: Tokenize T-SQL using TSqlParser (Microsoft.SqlServer.TransactSql.ScriptDom)
  2. AST Construction: Full parse tree for all stored procedures, functions, triggers
  3. Data Flow Analysis: Track parameter values through procedure bodies
  4. Control Flow Analysis: Map CASE/IF/WHILE/CURSOR control structures
  5. Cross-Procedure Call Graph: Resolve EXEC calls and dynamic SQL where possible
  6. Schema Dependency Graph: Map procedure → table → column access patterns
  7. Business Logic Extraction: Isolate computational logic from infrastructure SQL

8.1.3 Architecture Recovery

Pattern Detection on USKG:

  • God Class Detection: Classes with >500 methods or coupling score above threshold
  • Anemic Domain Model: Domain classes with only getters/setters, no behavior
  • Repository Pattern Violations: Data access logic outside repository boundaries
  • Service Locator Anti-pattern: Manual DI resolution in business logic
  • Big Ball of Mud Detection: Cyclomatic coupling analysis across the call graph
  • Strangler Fig Opportunity Mapping: Services with clean external interfaces ready for extraction

8.1.4 Configuration Recovery

Legacy .NET systems store critical business configuration in:

  • web.config / app.config — connection strings, feature flags, business parameters
  • Database configuration tables — business rule parameters
  • SSIS package parameters — ETL business rules
  • Registry entries — installation-time business configuration

NEXUS extracts all configuration into a typed, versioned configuration catalog with documentation and migration plans to modern configuration management (Azure App Configuration, HashiCorp Consul).

10.1.3 Adversarial Reviewer Agent

Design Rationale: No agent should review its own output. An adversarial agent using a different model family and independent context assembly challenges every generation.

Protocol:

1. INDEPENDENT REGENERATION
   Adversarial agent re-derives solution from same USKG slice
   (Different model, different temperature, different prompt structure)

2. DIVERGENCE ANALYSIS
   Compare Synthesis output vs. Adversarial output
   Identify divergence points with evidence citations from USKG

3. CHAIN-OF-VERIFICATION (CoVe)
   For each divergence:
     a. Generate verification question: "Does X hold for this transformation?"
     b. Query USKG for evidence
     c. Execute behavioral oracle test for the specific behavior
     d. Reach verdict with confidence score

4. DEBATE PROTOCOL (if unresolved after CoVe)
   Round 1: Synthesis Agent argues for its version (with USKG citations)
   Round 2: Adversarial Agent argues against (with USKG citations)
   Round 3: Arbiter LLM (third model family) evaluates
   Unresolved → Human Architect escalation

5. STRUCTURED CRITIQUE REPORT
   Confidence scores per divergence
   Evidence package with USKG node references
   Recommendation: APPROVE / REVISE / ESCALATE

11.1 The NEXUS Anti-Hallucination Architecture

Hallucination in code generation is not primarily an LLM quality problem — it is an architecture problem. The wrong input architecture causes correct models to generate wrong outputs. NEXUS addresses hallucination at the architectural level:

Control Mechanism Impact

Model Specialization Routing Right model for right task Eliminates out-of-distribution generation

Control Mechanism Impact
Self-Consistency (N=5) Multiple independent generations; consensus selection 60%+ reduction in single-pass errors

Adversarial Review Independent agent challenges every output Catches hallucinations the primary agent cannot self-detect
Debate Protocol Structured debate with USKG evidence citations Forces factual grounding in all arguments
Chain-of-Verification Systematic verification of each claimed fact Eliminates unverified assertions

11.1.3 Output Validation Controls (Eliminate Hallucination Before Commitment)

Control Mechanism Detection Rate
Roslyn Compilation Immediate syntactic/semantic rejection 100% for compilation errors
Behavioral Oracle I/O matching against production-derived golden dataset ~95% behavioral deviation detection

Knowledge Graphs act as a factual constraint. If the graph does not contain a relationship between components, the retrieval layer will not provide that context, significantly reducing the likelihood of the LLM fabricating a feature. Research highlights that this structural grounding is the most effective method for mitigating hallucination in domain-specific applications.

Problem Analysis

Large regulated organizations harbor decades of technical debt within their legacy .NET and SQL Server ecosystems. These applications exhibit specific anti-patterns that render standard modernization approaches highly dangerous. The fundamental limitations of migrating these systems stem from the semantic drift that occurs when translating across programming paradigms. Legacy applications heavily utilize T-SQL stored procedures to execute complex, procedural business logic directly within the data tier2. Attempting to lift this logic into a modern, object-oriented, cloud-native C# application layer requires translating procedural relational algebra into domain-driven, functional paradigms, often utilizing Object-Relational Mappers (ORMs) such as Entity Framework Core.

Manual rewrites introduce human error and fail to capture undocumented edge cases, leading to catastrophic regressions9. Conversely, applying pure generative AI to translate code results in hallucinations, where the model generates syntactically plausible but behaviorally divergent logic3. Legacy systems completely lack accurate documentation; the true system architecture and business rules are defined solely by the compiled Microsoft Intermediate Language (MSIL) and the dynamic execution paths of the stored procedures11. Furthermore, these systems lack comprehensive automated test coverage, eliminating the possibility of utilizing traditional test-driven validation during the modernization process10.

Research Survey

The transformation of legacy systems requires synthesizing multiple computer science domains, analyzing where existing techniques succeed and where they encounter fundamental limits.

The utilization of pure LLM code generation provides exceptional capabilities for semantic abstraction, natural language summarization, and boilerplate generation13. However, LLMs suffer from high hallucination rates, a lack of mathematical correctness guarantees, and an inability to process full-repository context effectively across thousands of interdependent files3. Deterministic AST parsing, conversely, offers mathematically precise structural translation and is entirely reproducible15. Yet, AST transformations are semantically blind; they cannot infer business intent, extract Domain-Driven Design (DDD) boundaries, or restructure logic beyond predefined heuristic rules14.

In the domain of architecture recovery, graph-based clustering algorithms analyze structural coupling. For verification, formal methods utilizing SMT solvers (such as Z3) provide mathematical proofs of behavioral equivalence between two program states by comparing formulae produced by symbolic execution20. While providing absolute certainty, these methods suffer from state-space explosion when analyzing unbounded loops or massive monolithic state spaces22. To bridge the gap where formal verification becomes computationally prohibitive, mutation testing frameworks like Stryker.NET validate the efficacy of test suites by injecting synthetic faults into the modernized code, ensuring the AI-generated tests are capable of detecting regressions10.

Layer 2: Formal Behavioral Equivalence (Symbolic Execution)

Drawing from advanced methodologies in translation validation (e.g., Heimdall and Cinder), the factory formally compares the legacy MSIL to the modern .NET 8 MSIL7.

  1. The code is lifted into an intermediate mathematical representation.

  2. Symbolic execution engines generate path constraints representing the logic flow.

  3. The Z3 SMT Solver evaluates the constraints, checking for mathematical equivalence between the legacy and modern implementations6. If the solver identifies a divergent execution path, it generates a concrete counter-example, which is immediately returned to the LLM for correction.

Layer 3: Dynamic Mutation Testing

Because formal verification via SMT solvers suffers from state-space explosion when analyzing complex, unbounded loops, the platform requires a robust testing fallback22. The Code Generation Agent writes extensive xUnit test suites based on the recovered business rules. These tests are then evaluated using Stryker.NET, an advanced mutation testing framework10. Stryker injects synthetic faults (mutants) into the modernized code (e.g., changing >= to <). If the LLM-generated tests fail to fail (i.e., the mutant survives), the test suite is deemed inadequate. The LLM is forced to generate edge-case specific tests until a 100% mutation kill rate is achieved, guaranteeing high confidence in the test suite's ability to catch regressions24.

While an improvement over single-prompt RAG, these frameworks still rely entirely on probabilistic LLM evaluation. This approach is rejected for production due to poor cost-efficiency and lack of mathematical validation.

The third candidate, Static Compiler-Based Translation Tools, relies on deterministic rules engines to convert syntax from old frameworks to new ones. While highly accurate for syntax mapping, these tools completely lack the semantic understanding required to decouple monolithic architectures into microservices, extract business intent from deeply nested procedural code, or redesign legacy data access patterns into modern Entity Framework Core paradigms15. Architecture Decision Record (ADR)

The following records document the major structural decisions establishing the recommended architecture.

ADR 1: Multi-Agent Orchestration Framework

  • Context: The system requires a sophisticated orchestration engine capable of managing state, context, and dynamic handoffs between specialized agents working to modernize legacy C# code.

  • Problem: Previous attempts using LangGraph failed due to probabilistic routing loops, poor integration with native .NET memory spaces, and high token overhead.

  • Candidate Options: LangGraph, CrewAI, Microsoft AutoGen, Microsoft Semantic Kernel.

  • Evaluation Criteria: Native .NET/C# compatibility, robust enterprise support, strict typing for plugin integration, and advanced multi-agent routing capabilities.

  • Pros/Cons: LangGraph and CrewAI possess strong Python ecosystems but introduce significant friction when wrapping .NET compiler APIs. AutoGen pioneered the Magentic-One pattern but has entered maintenance mode18. Semantic Kernel provides idiomatic C# integration, strong typing for native plugins, and robust Magentic orchestration natively supported by Microsoft21.

  • Risks: Semantic Kernel has a steeper learning curve for teams exclusively familiar with Python-based AI frameworks.

  • Final Decision: Microsoft Semantic Kernel.

  • Justification: For a system tasked with modernizing .NET code, utilizing a .NET-native orchestrator is mandatory. Semantic Kernel allows direct, in-process execution of Roslyn compiler APIs as native C# plugins, eliminating inter-process communication overhead and enabling deeply integrated Magentic orchestration for dynamic agent collaboration25.

ADR 2: Business Logic Extraction Methodology

  • Context: Legacy monoliths contain business rules buried in unstructured, tightly coupled procedural code (e.g., ASP.NET Web Forms or WCF)27.

  • Problem: Naive text scraping or pure LLM ingestion results in context window overflow, truncation of critical rules, and hallucinations of relationships.

  • Candidate Options: Regex/Text parsing, Pure LLM Long-Context Window processing, Abstract Syntax Tree (AST) traversal.

  • Evaluation Criteria: Deterministic accuracy, preservation of hierarchical dependencies, and token efficiency.

  • Pros/Cons: LLM long-context ingestion is highly expensive and prone to the "lost in the middle" phenomenon29. AST traversal requires building complex compiler plugins but yields 100% accurate metadata regarding types, method signatures, and database calls7.

  • Risks: Custom AST walkers require deep knowledge of the target language's syntax grammar.

  • Final Decision: Roslyn AST Traversal via SyntaxWalker.

  • Justification: By utilizing Microsoft's Roslyn compiler API to mathematically walk the legacy AST, the system extracts a precise, graph-like structure of the application. This metadata is formatted into Markdown (which LLMs parse exceptionally well) to provide a deterministic, hallucination-free grounding context for the generative models7.

ADR 3: Code Generation Verification

  • Context: Generative models, even advanced reasoning models like o3, occasionally produce code with subtle syntax errors, missing using directives, or type mismatches.

  • Problem: Relying on human developers to fix minor compilation errors negates the productivity benefits of AI generation. Relying on an LLM "reviewer" to spot syntax errors visually is highly unreliable.

  • Candidate Options: Probabilistic LLM Review, Static Linting, Dynamic In-Memory Compilation (Compiler-in-the-Loop).

  • Evaluation Criteria: Guarantee of functional validity, automation capability, and speed of feedback.

  • Pros/Cons: LLM review burns tokens and frequently misses missing references. In-memory compilation provides absolute proof of syntactic validity and generates exact, actionable error codes9.

  • Risks: In-memory compilation requires mocking or providing the full dependency graph of the target modern API framework.

  • Final Decision: Dynamic In-Memory Compilation via Roslyn CSharpCompilation.

  • Justification: The Verification Agent attempts to compile the LLM's raw C# output. If it fails, the agent parses the emitResult.Diagnostics (e.g., CS1061: Type 'X' does not contain a definition for 'Y') and feeds the exact error back to the Generator Agent9. This neuro-symbolic loop guarantees that code reaching the human reviewer is structurally sound.

ADR 4: Cost Optimization and Token Precision

  • Context: Repetitively processing massive legacy ASTs and architectural instructions during multi-agent loops results in unsustainable API inference costs.

  • Problem: Multi-agent frameworks often rebuild the prompt context on every single turn, negating any caching benefits and burning budget19.

  • Candidate Options: Context summarization (lossy), Selective retrieval (RAG), Azure OpenAI Prompt Caching.

  • Evaluation Criteria: Cost reduction, context preservation, and latency improvement.

  • Pros/Cons: Summarization sacrifices precision. Azure OpenAI Prompt Caching offers 50% to 75% input token discounts and drastically reduces Time-to-First-Token (TTFT), provided the prompt structure remains static at the beginning6.

  • Risks: Developers must strictly adhere to prompt engineering rules; any dynamic text injected early in the prompt invalidates the entire cache24.

  • Final Decision: Azure OpenAI Prompt Caching with Strict Prefix Ordering.

  • Justification: By structuring prompts such that the System Instructions, Tool Schemas, and the massive Markdown AST Knowledge Graph are placed at the absolute beginning of the context window, the system achieves a massive cache hit rate. Dynamic elements (like current agent dialogue or compilation errors) are strictly appended to the end, securing up to an 80% reduction in API costs without sacrificing accuracy6.

ADR 5: Developer Workflow Integration

  • Context: Developers must review, test, and accept the modernized API code without breaking their flow state.

  • Problem: Forcing developers into a separate web dashboard creates friction and isolates the modernized code from the actual repository and local test runners.

  • Candidate Options: Custom Web Portal, GitHub Pull Requests, VS Code Extension via Model Context Protocol (MCP).

  • Evaluation Criteria: Seamless developer experience, deep editor integration, and security.

  • Pros/Cons: Pull Requests are asynchronous but lack real-time conversational adjustment. MCP allows the centralized Semantic Kernel backend to securely expose tools directly to the developer's local VS Code instance, enabling rich, contextual interactions12.

  • Risks: MCP is a maturing standard requiring careful management of permissions and local filesystem access33.

  • Final Decision: VS Code Extension utilizing MCP (vscode.LanguageModelTool).

  • Justification: This approach integrates the modernization engine directly into the IDE. Developers can highlight a legacy file, invoke the MCP agent, and receive a modernized API implementation directly injected into a split-diff view for immediate review, testing, and commitment12.

Microservices and API Specifications

The platform relies on decoupled microservices communicating via gRPC for high-throughput internal operations and RESTful endpoints for external MCP clients.

  • Orchestrator Service: The central brain utilizing Semantic Kernel. Exposes endpoints for initiating modernization jobs, tracking status, and managing agent state22.

  • Compiler Service: A heavily sandboxed service that executes CSharpCompilation.Create. It receives virtual file strings and returns either a success boolean or a structured JSON array of Diagnostic objects detailing compilation errors9.

  • Knowledge Graph Service: Manages the persistence and querying of the Code Property Graph (CPG) and Program Dependence Graph (PDG).

Storage Strategy: Graph, Vector, and Caching

  • Graph Database (Azure Cosmos DB for Apache Gremlin): Legacy systems are networks of dependencies. The AST is mapped to vertices (Classes, Methods, SQL Tables) and edges (Calls, Inherits, Joins). This enables the Planner Agent to query exactly which database tables are impacted by a specific legacy method1.

  • Vector Database (Azure AI Search): Stores semantic embeddings of the extracted code. This is used for traditional RAG when a developer asks "Where is the authentication logic?"35.

  • Semantic Caching (Azure Cache for Redis): Caches frequent LLM responses and embedding pairs. If two agents request an analysis of identical legacy utility classes, the semantic cache intercepts the request, returning the result in milliseconds and saving token costs36.

Security, Observability, and Operations

  • Security: The system enforces Zero Trust. All Azure services communicate over private endpoints. No API keys are stored in code; the system relies exclusively on Microsoft Entra ID (Managed Identities)22. The Compiler Service runs in a Hyper-V isolated container to prevent malicious code execution during dynamic analysis.

  • Observability: Application Insights and OpenTelemetry trace the entire multi-agent workflow. Custom metrics track cached_tokens ratio, Time-to-First-Token (TTFT), and agent loop iterations24.

  • CI/CD & Deployment: Deployed via GitHub Actions to Azure Container Apps, utilizing KEDA to scale the orchestrator from zero based on modernization queue depth36.

  • Disaster Recovery & Multi-Region: Cosmos DB and Azure Cache for Redis utilize active-geo-replication. Azure OpenAI deployments are load-balanced across multiple regions to mitigate quota limits and regional outages.
